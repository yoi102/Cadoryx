# M8 大模型交互与操作体验

## 范围

M8 的目标是让已经导入的较大文档尽快出现可导航的画面，并在剩余实例提交期间保持窗口能响应输入。它不改变 BRep、装配或文件格式。当前实现采用每视口独立的分批场景提交：首批最多 32 个实例或 35 ms 原生工作（单个不可中断原生调用可能超出预算）；后续批次在 WPF `Background` 优先级让出 UI。相机在首批提交前用整个场景的包围范围定位，避免先放大局部再跳到全局。状态栏在首批原生调用之前就显示 `已显示/总数`，完成后恢复就绪状态。

原生 `OcctViewer.Display` 已将 AIS 对象以 `toUpdateViewer=false` 提交；Cadoryx 在首批、约每 450 ms 和完成时显式刷新。每个视口仍只持有自身的 OCCT 文档；同视口内按资产和 XDE 上下文复用几何资源。切换文档、视口销毁或场景变更会使旧批次失效，释放未完成批次的原生资源。较小场景和已有场景的编辑仍使用原来的原子 `SetScene` 路径。

初始相机按每个实例的已放置包围角点计算，避免先把全场景合成世界轴对齐框、再投影一次带来的额外留白。计算仍保留约 15% 的边缘余量，确保任何角点不被裁切。原生 FitAll 可以得到更紧的视图，但需要在完整场景建成后才有目标；M8 不为了提前求它而让画面先跳到一个中间相机。

## 验收口径

- 同一主机、相同版本、同一个 `MiniPC3.step` SHA-256 输入，对比 M6 基线（88,258,425 B；加载约 53.7 s；首次完整场景提交约 9.1 s）。分别报告首批提交、完整提交和截图耗时，不将 CPU 提交时间称为显示器帧率。
- 保留小零件、1000 重复实例和 `11WiFi.step` 三档回归，双视口清空/重建、相机转动、截图、内存与句柄趋势以及源文件哈希；每轮清空后原生几何、XDE 和标注归零，关闭后资产归零。
- 在首批后让出 UI 消息循环；场景切换或中途取消不得留下旧对象，也不得把部分显示状态写入文档。基准的输入优先级回调只证明批次之间可以处理消息，不能代替从物理鼠标输入到屏幕画面的端到端延迟测量。
- Release 构建、全量测试、发布版桌面冒烟与独立 NuGet 消费统一验证。物理混合 DPI、RDP 与数小时运行单独记录；没有设备证据时不宣称通过。

## 性能边界

STEP 内核导入仍是独立工作进程，MiniPC3 的约 55 s 导入成本没有因分批显示而消失。单个 OCCT 原生调用不可从 UI 线程中途抢占；每批时间预算只能约束两个调用之间的停顿。分批显示改善首次反馈与输入响应，完整场景提交可能因多次刷新比一次性提交更慢。需要以报告中的两个时间分别评价，不能用首批数字冒充完整加载完成。

基准对四档样本均强制调用分批视口 API，以覆盖同一资源生命周期；桌面产品对不足 300 个实例的场景仍走一次性原子提交，因此小零件和 `11WiFi.step` 表中的“首次非空”不代表其日常 UI 会显示部分场景。

`MiniPC3.step` 的 SHA-256 为 `f3773a7f37bd0cb8e717e4be6f1070a72e5c6e7b2f36f26f9501183df8c4c68e`，去重几何面数 35,960；首批受原生调用预算约束，实际上只提交了 1 个实例，**不代表模型已全部显示**。M6 相同输入的首次完整场景提交为 9,096.34 ms；本轮首次非空反馈提前约 86.1%，完整提交慢约 6.6%。转动 P95 37.70 ms，与 M6 的 36.81 ms 同量级。20 轮观测私有内存 2,851–2,922 MiB，不能由此证明任意长时间无泄漏。

本阶段的工程交互范围已验收。尚未取得物理混合 DPI、RDP 重连和数小时人机操作证据；尚未对 STEP 内核导入算法提速，也没有新增复杂草图操作手柄、通用配合或工程图数据结构。这些能力在后续阶段单列，不由“首帧 1.26 秒”推断已经完成。
